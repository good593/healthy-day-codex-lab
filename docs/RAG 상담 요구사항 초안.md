# RAG 상담 요구사항 초안

대상 사용자와 상담 범위를 합의하기 위한 초안입니다. 확정한 요구사항과 결정 근거는 `project/docs/requirements/rag-chatbot.md`에 기록합니다.

## 출발점과 정해진 조건

상품 조회 프로젝트에 자연어 질문을 입력하고, 검수한 문서를 검색해 답변과 출처를 확인하는 상담 화면을 추가합니다. 원문 RF-3.1~3.3이 대상이며 API·실패 처리 계약은 [RAG 구현 명세](<RAG 구현 명세.md>)를 따릅니다.

- Python 3.13·uv·FastAPI·Streamlit·SQLite와 기존 상품 조회를 유지합니다.
- 실제 생성기는 Groq입니다. Codex의 개발용 모델 설정과 구분합니다.
- 상담 이력 영구 저장, 로그인, 복용량 계산, PostgreSQL 전환은 제외합니다.
- 실제 상담에는 검수한 공식 자료만 사용합니다. 근거 없이 답을 만들지 않습니다.
- 구현 전에 요구사항을 기록하고, 계획 후 작은 단위로 구현·검증·커밋합니다.

## 인터뷰에서 결정할 질문

| 질문 | 답변에 남길 내용 |
| --- | --- |
| 첫 버전의 사용자는 누구인가? | 사용 상황과 질문의 수준 |
| 상담 주제는 어디까지인가? | 답변할 질문 3개와 제외할 질문 2개 |
| 어떤 문서를 사용할 것인가? | 문서명·기관·URL·원문 위치·검수 상태 |
| 문서가 답을 제공하지 않으면? | 부족 안내와 추가 질문 유도 문구 |
| 문서 본문에 지시문이 있으면? | 근거를 명령으로 실행하지 않는 기준 |
| 질문·답변·인용은 어디에 표시할 것인가? | 상품 화면과 상담 화면의 관계 |
| 이전 대화를 다음 질문에 전달하는가? | 첫 버전의 단일 질문 처리와 세션 표시 범위 |
| 장애 안내와 재시도는 어떻게 제공할 것인가? | 화면 문구와 사용자의 다음 행동 |
| 무엇으로 완료를 판단하는가? | 테스트·수동 확인·실제 호출 기준 |

코드에 답이 있는 질문은 저장소를 먼저 조사합니다. 담당자가 결정할 조건에는 추천안과 이유를 함께 제시합니다. 앞선 결정에 의존하는 질문은 그 결정 후에 다룹니다.

## 인터뷰 종료 기준

정상·근거 부족·장애 사례와 제외 범위를 설명할 수 있고 미결 질문의 담당자·해결 시점이 정해져 있어야 합니다. 미결 조건을 확정된 고객 요구사항으로 기록하지 않습니다. 기술 구현 방식은 요구사항 합의 후 구현 계획에서 검토합니다.
