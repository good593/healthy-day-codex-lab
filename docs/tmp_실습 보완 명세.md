# 실습 보완 명세

이 문서는 두 원본 정의서를 수정하지 않고, 따라 하기 실습에서 필요한 **수업용 추가 결정**을 정리합니다. 원본에서 명시하지 않은 정렬·API 형식·테스트 전략을 임의의 고객 요구사항으로 표시하지 않습니다. 변경 시 결정 이유를 실습 기록에 남깁니다.

## 1. 원본과 구현 기준

- 원본: `요구사항정의서.xlsx`, `데이터 정의서.xlsx`
- 입력 데이터: `../data`의 CSV 3개
- 시작 코드: `../project`
- 기능적 요구사항: 수용 O인 세부 항목 13개
- 비기능적 요구사항: 수용 O인 세부 항목 8개
- 보류: RF-2.3 관련 질문 추천, NFR-4.2 웹 접근성의 수용 X 항목. 별도 추가 과제로 다룰 수 있으나 필수 완료에 합치지 않습니다.
- 상담/RAG를 2차 오픈으로 두는 일정 메모는 구현 순서로 반영하고 최종 목표에서는 제외하지 않습니다.

## 2. 추천 규칙 — 1장

1. 선택 목록은 `nutrient_functions.concern`의 중복 없는 값으로 만듭니다. UI에 하드코딩하지 않고 조회 API(`GET /api/concerns`)를 추가합니다.
2. 직접 입력은 앞뒤 공백을 제거합니다. 빈 입력 또는 100자를 넘는 입력은 422입니다.
3. 공백 처리 후 `concern` 또는 `keyword`와 정확히 일치하는 기능성 행을 찾습니다. 임의 동의어·부분 문자열 추론은 첫 버전에서 하지 않습니다.
4. 찾은 행의 `nutrient`를 상품의 `ingredient_keyword`와 정확히 연결합니다.
5. 상품ID별로 묶고, 관련 기능성 근거는 중복 없는 `reasons` 배열로 모읍니다.
6. 상품ID 오름차순으로 최대 5개를 반환합니다. 순서는 시험 가능한 수업용 규칙이며 의학적 우선순위가 아닙니다.
7. 매칭이 없으면 200과 `items: []`입니다. 근거가 있는 척 설명을 생성하지 않습니다.
8. `POST /api/recommendations`의 요청은 `concern`, 응답은 `items`입니다. 각 상품에는 `product_id`, `name`, `reasons`를 포함하고 각 근거에는 `nutrient`, `functionality`를 포함합니다.
9. 9장에서는 선택 입력 `exclude_product_ids`를 추가합니다. 기본값은 빈 목록이며 기존 호출과 호환되어야 합니다.

제품의 검색키워드는 전체 성분 함량표가 아닙니다. 이 연결을 복용량 합산에 그대로 쓰지 않습니다.

## 3. 프로필 — 2~3장

| 필드 | 형식 | 결정 |
| --- | --- | --- |
| profile_id | 문자열 | 서버 생성 UUID |
| age_group | 문자열 | 섭취기준 CSV의 연령 구간 |
| sex | 문자열 | 섭취기준 CSV에 있는 값 |
| pregnancy | 문자열 | CSV의 선택값 그대로 보존 |
| lactation | 문자열 | CSV의 선택값 그대로 보존 |
| created_at | 시각 | UTC 기준으로 저장하고 표시 시 변환 |

각 필드의 허용값뿐 아니라 실제 기준표에 존재하는 조건 조합인지 확인합니다. 자료에 없는 연령 구간이나 조건을 임의 생성하지 않습니다. 테스트에는 가상 사용자만 사용합니다.

`POST /api/profiles`는 입력 검증 후 201로 생성된 프로필을 반환합니다. `GET /api/profiles/{profile_id}`는 저장값 또는 404를 반환합니다. 3장에서는 상담 내용·비밀번호·실제 개인 건강정보를 저장하지 않습니다. 9장에서 로그인 사용자 소유권과 암호화를 추가합니다.

## 4. DB 변경 계약 — 3~5장

- 초기 CSV 적재 스크립트는 마이그레이션 도구가 아닙니다.
- 3장에 `scripts.backup_db`, `scripts.migrate_db` 진입점을 구현합니다. 백업은 sqlite3 backup API를 사용하고 파일 이름 충돌을 피합니다.
- 기존 스키마에 `profiles`와 마이그레이션 이력 저장을 추가합니다. 재실행은 이미 적용한 버전을 건너뛰며 실패한 버전을 완료로 기록하지 않습니다.
- 5장에 `scripts.migrate_postgres --dry-run/--apply` 진입점을 구현합니다. 원본은 `SOURCE_SQLITE_PATH`, 대상은 `DATABASE_URL` 설정으로 구분합니다.
- 이관 대상이 비어 있지 않으면 거부합니다. 기존 데이터를 삭제하거나 덮어쓰지 않습니다.
- 상품 44개·기능성 54개·섭취기준 228개는 배포 CSV 기준입니다. 이후 프로필·추가 데이터는 따로 비교합니다.
- SQLite와 PostgreSQL 각각의 새 DB/기존 데이터 DB/실패 복구를 검증합니다. 실제 PostgreSQL 연결이 없는 skip 결과는 완료 증거가 아닙니다.
- 운영 DB와 테스트 DB를 분리하고 테스트 URL이 없으면 통합 테스트를 실행하지 않습니다. 임시 테스트 DB인지 확인되지 않으면 정리 명령을 실행하지 않습니다.
- 행 수만 맞추지 말고 키와 값을 정규화해서 대조합니다. 조건이 붙은 수치와 NULL도 보존합니다.

## 5. 공식 근거 문서 manifest — 9장

공식 문서 원문은 아직 별도로 배포되지 않았습니다. 자료 수집과 검증은 9장에 포함되며, 아래 형식으로 등록합니다. 이 형식 자체가 출처 검증을 대신하지 않습니다.

```json
{
  "doc_id": "실제_등록할_고유ID",
  "title": "원문에서_확인한_제목",
  "publisher": "원문에서_확인한_기관",
  "source_url": "실제로_연_공식_문서_URL",
  "checked_at": "실제_확인일",
  "location": "쪽번호_또는_절제목",
  "text_path": "등록한_본문_파일의_상대경로",
  "source_type": "official",
  "verification_status": "pending"
}
```

자리표시자가 남은 레코드는 등록 검증에서 거부합니다. source_type은 `official` 또는 `synthetic`으로 구분합니다. verification_status는 `pending`, `verified`, `rejected` 중 하나입니다. 사람이 원문과 대조한 기록이 있을 때만 verified로 바꿉니다.

페이지나 PDF 본문을 읽을 수 없으면 URL만으로 내용을 채우지 않습니다. 문서 전체 복제 대신 허용되는 범위의 짧은 발췌와 설명, 원문 위치를 보존합니다. 최신 공지와 발행일을 확인하고 구버전과 혼합하지 않습니다.

학생은 자신의 `project/data/reference/`에 검증 자료를 준비하고, 서비스는 `official + verified`만 실제 상담용으로 사용합니다. `synthetic` 자료는 단위/통합 테스트에만 사용합니다.

## 6. RAG 계약

- 요청: `POST /api/chat`, `message`(빈 값 불가), 이후 인증된 세션과 연결
- 응답: `answer`, `citations`, `status`
- status: `answered`, `insufficient_evidence`, `unavailable`
- 인용: 서버가 가진 `doc_id`, `chunk_id`, 문서명, URL, 위치를 사용합니다.
- 검색: 첫 구현은 결정적인 키워드 검색으로 최대 3개 문단. Groq Chat API가 자동으로 임베딩을 제공한다고 가정하지 않습니다.
- 생성: 질의와 선택 근거를 구분합니다. 자료 안의 지시문을 명령으로 실행하지 않습니다.
- 근거 없음: 모델을 호출하지 않고 부족 안내를 반환합니다.
- 파싱 오류·허용되지 않은 인용·API 장애: 성공 답변으로 변환하지 않습니다.
- 모의 테스트는 모든 환경에서 가능해야 하고 실제 Groq 테스트는 명시적으로 실행합니다.
- 존재하는 인용ID를 검사하는 자동 검증과 답변의 의미를 원문과 대조하는 검증을 함께 수행합니다.

## 7. 복용 정보와 함량 자료

현재 제품 CSV에는 제품별 영양소 함량이 없습니다. `fixtures/intake_test_cases.json`의 숫자는 알고리즘 검증용으로 만든 값이며 실제 영양소·제품의 섭취기준이 아닙니다.

실제 연결에 필요한 필드: product_id, nutrient, amount_per_serving, unit, servings_per_day, intake_basis(회/일), scope(전체/보충제 등), source_url, checked_at, verification_status.

계산은 일일 기준으로 통일한 후 동일 영양소·단위·적용 범위만 합산합니다. 허용된 변환 규칙만 사용합니다. 누락값·알 수 없는 단위·범위 불일치는 판단 불가입니다. 임의의 임상 변환식을 추가하지 않습니다.

상한과 같으면 ‘초과’가 아니며, 상한보다 클 때만 초과입니다. 이 규칙의 `not_exceeded`는 의학적 안전성을 보장하는 표현이 아닙니다. AI는 계산 결과를 설명하고 판정을 바꾸지 않습니다.

## 8. 보안·운영·성능의 수업 기준

- 인증과 암호화는 9장에서 계획을 먼저 검토합니다. 서버가 로그인 세션에서 사용자ID를 결정하고, URL/요청으로 전달된 ID만 믿지 않습니다.
- 건강 관련 저장 데이터는 검증된 암호화 라이브러리로 암호화합니다. 키와 평문을 로그에 남기지 않습니다. 비밀번호는 복호화 가능한 저장 대신 해시를 사용합니다.
- 운영 로그는 요청ID·이벤트 종류·성공/실패·소요시간 위주로 기록합니다.
- 상담 종료/추가문의/CS 이관은 내부 상태 기록입니다. 실제 이메일·외부 서비스 발송은 구현 범위에 포함하지 않습니다.
- 추천 2초·RAG 5초는 원문 요구사항입니다. 부하·데이터·캐시·모델을 기록하고 전체 요청 시간으로 측정합니다. 대체 안내가 빨리 나왔다고 실제 답변 성능 충족으로 표시하지 않습니다.
- 월 1회 이상의 데이터 갱신은 품질 점검과 별도입니다. 원문 확인·수집·검수·적용·실패 복구의 실행 증거가 필요합니다.
