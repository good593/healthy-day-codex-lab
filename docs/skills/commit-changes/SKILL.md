# 검증한 변경 커밋

계획의 구현 단위와 검증 기록에 맞는 파일을 하나의 설명 가능한 커밋으로 묶는다.

## 입력

구현 단위, 계획, 검증 기록, 선택한 파일·메시지, 준비만 할지 실제 커밋할지를 현재 요청에서 확인한다. 이 프로젝트에서는 `project/docs/plans/rag-chatbot.md`와 `project/docs/reports/`의 기록을 사용한다. 경로는 실제 Git 루트와 현재 폴더에서 해석한다.

## 절차

1. 적용 지침과 계획을 읽고 Git 루트·브랜치·HEAD·상태를 확인한다. 커밋된 변경, staged/unstaged 변경과 새 파일을 조사해 이번 단위의 파일별 목적·커밋 후보를 제시한다. 명시된 파일·메시지가 있으면 그 선택을 따른다. `main`의 기능 커밋처럼 요청과 다른 대상이면 원인을 확인한다.
2. 검증 기록의 범위·명령·결과와 파일 manifest를 확인한다. 같은 포함 경로/제외 규칙으로 목록·해시를 재수집해 관련 파일의 추가·삭제·내용 변경을 비교한다. HEAD만 달라지고 검사 대상 내용이 같다면 기존 결과를 사용할 수 있다. 관련 소스·테스트·설정·lock·요구사항·입력 자료가 바뀌었거나 기록에 manifest가 없으면 기존 결과를 현재 검증으로 간주하지 않는다.
3. 검증이 오래되었거나 필요한 검증이 없으면 갱신할 항목을 제시한다. 이미 검증까지 요청받았다면 관련 검사를 수행해 기록을 갱신하고, 그렇지 않으면 재검증이 필요한 상태로 커밋 후보까지만 준비한다. 실패한 필수 검사나 완료 조건의 누락을 숨긴 채 커밋하지 않는다. 실제 자료·계정 부족 등 계획에서 허용한 미실행은 이유를 보존하고 그 제한이 드러나는 범위로 처리한다.
4. 전체 기능과 무관한 변경·사용자의 다른 작업·`.env`·DB·캐시가 후보에 섞이지 않았는지 확인한다. 기존 index에 다른 작업이 stage되어 있으면 그것을 임의로 해제하거나 함께 커밋하지 않는다. 이때는 충돌하는 파일·hunk를 설명하고 범위가 명확해질 때까지 후보 준비로 끝낸다. 한 파일에 여러 작업이 섞인 경우에도 필요한 hunk를 분리해 검토한다.
5. 준비만 요청받았다면 파일 목록·목적·검증 근거·제안 메시지와 주의할 hunk를 보고하고 끝낸다. index는 바꾸지 않는다. 커밋 요청이 이미 명확하면 중복 확인을 요구하지 않고 선택된 파일/hunk만 stage한다. `git add .`나 `git add -A`로 모든 변경을 묶지 않는다.
6. `git diff --cached --stat`, `git diff --cached`, `git diff --cached --check`로 실제 커밋 범위·내용·패치 오류를 확인한다. staged 내용이 검증한 작업 트리의 내용과 같은지 확인한다. 테스트 실행 후 다시 편집한 내용이나 부분 stage가 검증과 다른 상태를 만들었다면 먼저 그 상태를 검증한다. 코드 파일에서는 현재 작업 트리와 index의 차이도 확인한다.
7. 실제 동작에 맞는 메시지로 커밋하고 해시·포함 파일·남은 변경을 확인한다. hook 실패 시 원인을 보고하고 hook을 우회하거나 자동 amend하지 않는다. 검증 기록에 해시를 추가한다면 새 문서 변경임을 알리고, 후속 문서 커밋 요청 없이 방금 커밋을 수정하지 않는다.

## 완료 보고

준비 상태 또는 커밋 해시, 파일별 목적, 메시지, 사용한 검증 기록과 미실행 제한, 남은 staged/unstaged 변경을 보고한다. push·PR 생성은 별도 요청으로 진행한다.
