# 변경 검증

요청받은 범위의 완료 조건을 실제 변경과 실행 결과로 확인하고, 다음 커밋·PR에서 사용할 검증 기록을 남긴다.

## 입력과 프로젝트 경로

- 입력: 요구사항 문서, 구현 계획, 구현 단위 또는 전체 범위, 기준 브랜치, 기록 경로. 현재 요청과 계획에서 확인할 수 있는 값은 다시 질문하지 않는다.
- 이 프로젝트의 실행 폴더는 Git 루트의 `project`다. 요구사항은 `docs/requirements/rag-chatbot.md`, 계획은 `docs/plans/rag-chatbot.md`, 기본 기준은 `main`이다.
- 공통 명세·fixture·템플릿은 `../docs/`에 있다. Git 루트·현재 폴더를 확인하고 실제 경로로 해석한다.
- 기록 형식은 `../docs/templates/change-validation.md`를 사용한다. 단위별 기록 경로는 요청을 따르고 전체 검증의 기본 출력은 `docs/reports/rag-validation.md`다.
- 다른 프로젝트에서는 이 경로·명령을 그대로 가정하지 말고 적용 지침·계획·프로젝트 설정을 따른다.

## 절차

1. 적용되는 `AGENTS.md`, 요구사항, 계획과 관련 명세를 읽는다. Git 루트, 브랜치, HEAD, 기준 브랜치와의 merge-base를 기록한다. `git status --short`, 기준 대비 커밋된 diff, staged/unstaged diff와 미추적 파일을 확인한다. `git diff`에 나오지 않는 새 파일도 검증 범위에 포함한다.
2. 각 완료 조건을 구현 위치·테스트·수동 확인에 연결한다. 이번 단위 밖의 미구현 조건은 후속 단위로 표시한다. 누락된 테스트나 요구사항 불일치는 발견 사항으로 보고하고, 검증을 위해 애플리케이션 코드·테스트·설정·lock을 임의로 수정하지 않는다. 실행 부산물과 요청된 검증 기록 작성은 허용한다.
3. 검증 시작 전 검사에 영향을 주는 파일 목록과 SHA256을 수집한다. 범위에는 변경 파일뿐 아니라 관련 소스·테스트·설정·의존성 lock·요구사항·계획·입력 자료·CI를 포함한다. 전체 검증은 앱 소스·테스트·설정·lock과 관련 공유 자료 전체를 포함한다. `git ls-files`와 `git ls-files --others --exclude-standard`로 후보를 찾고 실제 입력 자료도 포함한다. 삭제 파일은 삭제 상태로 기록한다. `.env`·키·실행 DB·가상환경·캐시는 제외하며 비밀값을 읽거나 출력하지 않는다.
4. 기록할 manifest에는 포함 경로/제외 규칙과 파일별 상태·SHA256을 함께 저장한다. 나중에 새 파일의 추가·삭제도 탐지할 수 있게 파일 목록을 재수집할 수 있어야 한다. PowerShell에서는 `Get-FileHash -LiteralPath <실제 파일> -Algorithm SHA256`을 사용할 수 있다. 검증 보고서·PR 본문·작업 노트처럼 실행에 영향을 주지 않는 전달 문서는 manifest에서 제외하고 제외 이유를 기록한다.
5. 계획에서 정한 관련 테스트·회귀 검사와 품질 검사를 실행한다. 같은 검사 대상 상태와 실행 환경에 대한 유효한 기록이 있으면 시각·범위·명령을 대조해 결과를 연결할 수 있다. 아래 명령은 이 프로젝트의 기본이며 `project`에서 실행한다. 단위 검증은 실제 테스트 경로를 확인해 관련 테스트를 선택하고, 전체 검증은 기존·신규 테스트를 모두 실행한다.

   ```powershell
   uv run --locked python -m pytest -q --basetemp=.pytest_cache/tmp
   uv run --locked ruff check .
   uv run --locked ruff format --check .
   ```

6. 명령, 실행 위치, Python·도구 버전, 시각, 종료 코드, 통과·실패·skip 수를 기록한다. 실패한 검사는 원인·영향을 보고한다. 누락된 도구·자료·권한으로 실행하지 못했다면 미실행 이유와 재실행 조건을 적는다. 검사 비활성화나 실패 무시로 통과 처리하지 않는다.
7. 수동 API·화면·실제 외부 호출은 요청 범위와 준비 상태에 따라 수행한다. 사람이 확인한 결과는 제공받은 결과임을 표시한다. 모의 테스트, 연결 점검, 실제 상담·원문 대조를 구분한다. 자료·계정이 없는 실제 호출은 미실행으로 남긴다. 키·질문 원문·상담 내용을 기록하지 말고 사례 유형·관찰한 동작·모델·자료 버전만 적는다.
8. 검증 종료 후 같은 규칙으로 파일 목록과 해시를 다시 수집한다. 검사 대상이 도중에 바뀌었으면 영향을 받는 검사를 다시 실행하거나 결과가 현재 상태에 유효하지 않음을 표시한다. HEAD 변화 자체가 아니라 검사 대상 파일의 내용·목록과 기준의 변화를 근거로 판단한다.
9. 기록에 완료 조건별 충족·미충족·후속 단위·미실행을 남긴다. 새 결과로 이전 기록을 덮어써서 실패나 미실행을 없애지 말고 실행 이력을 보존한다. 구현 수정이 필요한 발견 사항과 커밋 가능 범위를 요약하고 끝낸다.

## 완료 보고

검증 범위·유효한 코드 상태·실제 실행 결과·미충족/미실행 항목·다음 작업·기록 경로를 보고한다. 테스트 통과와 기능 전체 완료를 구분하며 커밋·push·PR은 수행하지 않는다.
