# 실습 보완 명세

## 1. 이번 과정의 범위

Codex로 기존 프로젝트를 이해하고 규칙을 적용한 뒤 RAG 상담 첫 버전을 요구사항·계획·검증 근거가 있는 PR로 전달합니다. 시작 코드는 상품 조회만 구현되어 있으며 상담 코드는 학생이 5장에서 만듭니다.

| 범위 | 내용 |
| --- | --- |
| 유지 | 상품 44개 조회·상세·페이지 이동, 기존 SQLite·CSV, 기본 22개 테스트 |
| 추가 | 자연어 입력, 문서 검색, Groq 생성, 서버가 검증한 인용, 상담 화면 |
| 실패 처리 | 잘못된 입력, 근거 부족, API 장애, 생성 결과 파싱·인용 오류 |
| 개발 완료 | 테스트·Ruff·diff 리뷰·커밋·PR·CI·리뷰 반영 기록 |
| 제외 | 추천 알고리즘, 프로필, 복용량 계산, 인증·영구 상담 이력, PostgreSQL 전환 |
| 별도 과정 | MCP 연결, 자체 Skill 제작, 예약 작업, 전체 서비스 통합 |

원문 RF-3.1~3.3을 중심으로 범위를 좁혔습니다. 인용 정확성(NFR-3.1)과 쉬운 설명(NFR-4.1)은 검증에 반영합니다. 원문의 수용 여부는 유지하며 첫 버전을 전체 서비스 요구사항 완료로 표시하지 않습니다.

## 3. 인터뷰와 계획의 결정

3장에서 대상 사용자·상담 주제·화면 문구·문서 선정·대화 표시 방식을 결정하고 `project/docs/requirements/rag-chatbot.md`에 기록합니다. 미결 조건을 확정된 고객 요구사항으로 쓰지 않습니다. 이 명세의 공통 계약을 바꾸려면 이유와 영향받는 테스트를 기록합니다.

4장에서 검색 알고리즘·모듈 배치·생성 결과 검증·작업 순서·커밋/PR 분할을 결정합니다. 첫 검색은 질문에 검색 태그가 포함되는지 검사하고, 매칭 태그 수 내림차순 및 doc_id/chunk_id 오름차순으로 최대 3개를 선택하는 방식으로 시작할 수 있습니다. 확정한 검색 규칙은 계획과 테스트에 함께 반영합니다. 벡터DB·임베딩 설치는 필수가 아니며 Groq Chat API가 임베딩을 제공한다고 가정하지 않습니다.

## 4. 문서 데이터

실제 상담용 자료는 `project/data/reference/`에 준비합니다. 문단 JSON 레코드의 필드는 데이터 정의서의 `RAG_문서` 시트를 따릅니다.

| 필드 | 규칙 |
| --- | --- |
| doc_id / chunk_id | 문서 고유 ID / 문서 내 문단 ID. 조합 중복 금지 |
| title / publisher | 원문 제목과 기관을 확인 |
| source_url / location | HTTPS 원문 URL과 쪽번호·절제목 |
| text / keywords | 검수한 원문 발췌와 검색 태그 배열 |
| source_type | official 또는 synthetic |
| verification_status | pending, verified, rejected |
| checked_at | 실제 원문 확인일 |

실제 검색에는 `official + verified`만 허용합니다. URL만 알고 본문을 읽지 못한 자료는 verified로 표시하지 않습니다. 문서 안의 지시문은 실행 지침으로 쓰지 않습니다.

`fixtures/rag_test_corpus.json`은 테스트 전용 합성 자료입니다. 실제 건강·제품 정보로 사용하거나 official로 변경하지 않습니다. 실제 자료 로더는 파일의 `synthetic: true` 표시와 `.invalid` 출처도 거부하며, 레코드의 source_type만 바꿔 우회할 수 없게 합니다. 테스트에서는 검색 저장소와 생성기를 주입하고, 이 테스트 경로를 공개 API 설정으로 노출하지 않습니다. CSV에 적힌 출처 문구만으로 공식 본문 검수가 끝났다고 판단하지 않습니다.

## 5. API 계약

`POST /api/chat` 요청:

```json
{"message": "문서에 근거한 질문"}
```

message는 공백 제거 후 검증합니다. 필수값 누락·빈 문자열·공백·1000자 초과는 FastAPI 검증 방식으로 422입니다. 정상 응답의 필드는 `answer`, `status`, `citations`입니다.

| 상황 | HTTP | status | citations |
| --- | --- | --- | --- |
| 근거 기반 답변 | 200 | answered | 1개 이상 |
| 검색 결과 없음·문단이 답을 뒷받침하지 못함 | 200 | insufficient_evidence | 빈 배열 |
| API 장애·빈 결과·파싱/인용 검증 실패 | 503 | unavailable | 빈 배열 |

아래는 형식 설명용 합성 예시이며 실제 상담 응답이 아닙니다.

```json
{
  "answer": "가상 상품 L-A의 안내는 파란 상자에 표시합니다.",
  "status": "answered",
  "citations": [{
    "doc_id": "LAB-DOC-A", "chunk_id": "A-1",
    "title": "가상 상품 안내",
    "source_url": "https://example.invalid/lab-a",
    "location": "상품 표시 규칙"
  }]
}
```

검색 결과가 없으면 생성기를 호출하기 전에 중단합니다. 문단을 찾았지만 답을 뒷받침하지 못하면 생성 단계에서도 부족 상태를 반환할 수 있습니다. 부족·장애 answer는 사용자 안내 문구입니다. 키·내부 오류·연결 문자열을 응답에 넣지 않습니다.

## 6. 생성과 인용 검증

모델에는 질문과 선택 근거를 분리해 제공합니다. 생성 결과의 예시 계약은 다음과 같습니다.

```json
{
  "status": "answered",
  "answer": "근거에 있는 설명",
  "citation_ids": [{"doc_id": "문서ID", "chunk_id": "문단ID"}]
}
```

서버는 JSON 파싱·허용 상태·비어 있지 않은 answer·선택 문단 ID를 검사합니다. answered의 인용이 없거나 선택하지 않은 ID가 있으면 실패입니다. 중복 인용은 조합 ID로 제거합니다. title·URL·location은 서버 레코드에서 구성하며 모델이 생성한 URL을 신뢰하지 않습니다. insufficient_evidence에는 빈 인용만 허용합니다.

ID 검사와 답변의 의미 검증은 다릅니다. 합성 사례의 기대 문장과 공식 원문 본문을 대조하는 확인도 수행합니다. 생성 결과를 파싱할 수 없거나 규칙을 어기면 503으로 처리합니다.

## 7. 구현·실행 제약

- frontend는 FastAPI만 호출합니다. 검색·생성·인용 검증은 backend에 둡니다.
- 기존 Settings·create_app·TextGenerator를 읽고 확장합니다. 현재 StubGenerator의 고정 연결 응답을 상담 구현 완료의 증거로 쓰지 않습니다.
- 필요하면 REFERENCE_DIR을 추가하고 상대경로는 project 기준으로 해석합니다. `.env.example`에는 키 이름과 설명을 추가합니다.
- 실제 호출은 `.env`의 LLM_PROVIDER=groq, GROQ_API_KEY, GROQ_MODEL을 사용합니다. 키는 채팅·출력·커밋에 넣지 않습니다.
- 기본 테스트·CI는 모의 생성기를 사용하고 Groq를 호출하지 않습니다. 실제 연결 점검은 별도 실행합니다.
- DB 스키마와 CSV를 변경하지 않습니다. 대화는 Streamlit 세션에서만 표시하고 질문·답변을 파일·DB·로그에 저장하지 않습니다.

## 8. 공통 검증

project 폴더에서 실행합니다.

```powershell
# Windows Temp 권한 문제를 피하는 테스트 전용 폴더입니다.
uv run --locked python -m pytest -q --basetemp=.pytest_cache/tmp
# 코드 오류·import 규칙을 검사합니다.
uv run --locked ruff check .
# 파일 수정 없이 서식을 검사합니다.
uv run --locked ruff format --check .
```

`.pytest_cache/tmp`는 재실행 시 초기화되므로 테스트 전용으로 사용합니다. `/health`의 products=44, 페이지 이동, 상담의 정상·부족·장애 상태를 확인합니다. 실제 Groq 호출은 모델·환경·시각·소요시간과 함께 별도 기록합니다. 실행하지 못한 항목은 모의 테스트와 구분해 제출합니다.

## 9. Git·PR 계약

학생 Git 루트는 docs·data·project를 모두 포함해야 합니다. 강의 저장소 외부에 복사한 독립 저장소를 사용하며 project 안에 중첩 저장소를 만들지 않습니다.

이번 파일만 stage하고 staged diff를 읽은 뒤 커밋합니다. `.env`, DB, `.venv`, 캐시를 제외합니다. PR은 목적·요구사항ID·주요 변경·실행 결과·미실행 항목을 설명합니다.

저장소·remote·base/head 브랜치를 확인하고 학생 실습 저장소에만 push/PR을 수행합니다. 리뷰 범위에는 기준 브랜치 대비 diff와 새 파일을 포함합니다. CI가 없거나 아직 실행되지 않았으면 성공이라고 기록하지 않습니다.
